# Final Engineering Summary

This is the project-level summary the assessment's §4.8 asks for: plan and
rationale, artifacts, risks/trade-offs/validation, assumptions, and
limitations — for the orchestrator submission as a whole. (Each individual
generated run also produces its own `docs/engineering_summary.md`, scoped to
that run — e.g. `target/docs/engineering_summary.md` — synthesized by the
`release` agent from that run's own decisions and findings.)

## Plan and rationale

Built in seven phases, each committed separately with its own detailed
rationale (`git log` on this repository is itself close to an audit trail of
the build): foundations (contracts, hash-chained ledger, sandboxed
workspace) → the DAG engine (frontier scheduling, gates) → governance
(policy, approvals, resilience, replanning, metrics) → the agent runtime
(providers, nine stage agents) → the target system CLI → the three demo
scenarios → this documentation.

The ordering was deliberate: the orchestration layer (§4.4 of the
assessment, called out as "Critical Differentiator") was built and proven
correct — with synthetic stub agents — *before* any agent contained real
domain logic. That is what makes the claim "the engine is generic, domain
knowledge lives only in the agents" verifiable rather than asserted: the
90-plus engine/governance tests that existed before a single line of
URL-shortener logic was written still pass unmodified.

Key rationale, condensed (see [ARCHITECTURE.md §6](ARCHITECTURE.md#6-key-design-decisions)
for the full list):

- Governance (policy, approvals, retry/rollback) is enforced by the *engine*
  on every stage, not opt-in per node — a guardrail that can be forgotten is
  not a guardrail.
- Agents never mutate run state; they return a result and the engine decides
  admissibility. That is the autonomy boundary, made structural rather than
  a convention.
- The system runs fully, reproducibly, and free with zero API calls by
  default; a real model is a config change, not a code change.

## Artifacts

- **The orchestrator** — `orchestrator/`: ~6,900 lines across contracts,
  config, CLI, the core engine/graph/gates/ledger/policy/approvals/
  resilience/replanning/metrics/workspace modules, three providers, and nine
  stage agents.
- **The target system** — `target/`: a working FastAPI URL shortener
  (SQLite repository, base62 codes, custom aliases, expiration, click
  analytics, rate limiting), its own pytest suite, an OpenAPI spec, and the
  full documentation/decision/risk trail the run that produced it left
  behind. Generated by the orchestrator, not hand-written — reproducible
  with `asdlc build`.
- **250 tests** (~3,200 lines) — unit and integration, covering the engine,
  every governance concern in isolation and composed, every agent, and every
  CLI command against real runs.
- **Documentation** — this file, [ARCHITECTURE.md](ARCHITECTURE.md),
  [SCENARIOS.md](SCENARIOS.md) (real transcripts of all three required
  scenarios), [TESTING.md](TESTING.md), and the root
  [README.md](../README.md).

## Risks, trade-offs and validation

Covered in depth in [TESTING.md](TESTING.md#trade-offs) and
[TESTING.md](TESTING.md#limitations). Summarized:

| Risk | Mitigation / validation |
|---|---|
| Deterministic heuristic misreads a requirement (can't detect negation) | Documented limitation; live-model path available; every misread is visible in the generated `docs/requirements.md`, not hidden |
| Brownfield impact analysis is lexical, not structural | Documented limitation; the analysis is always shown to the reviewer, never silently trusted downstream |
| Generated service has no auth, in-process-only rate limiting | Explicit, documented prototype-scope decision, flagged by the security agent in every run's own security review |
| A governance bug ships silently | Every governance primitive (retry, rollback, approval, policy, re-planning) has both isolated unit tests and at least one integration test running it through the real `Engine`; five real bugs were caught this way during development (see [TESTING.md](TESTING.md#bugs-the-tests-actually-found)) and each shipped with a regression test |
| Audit trail is tampered with or incomplete | Hash-chained ledger, `verify()`-able by any reviewer; a real run's chain is confirmed intact in [SCENARIOS.md](SCENARIOS.md) |

## Assumptions

- The three scenarios are demonstrated against a URL shortener, per the
  assessment's own scenario (§2); the orchestration layer itself is
  domain-agnostic (see [ARCHITECTURE.md §1](ARCHITECTURE.md#1-what-this-is)).
- "Runnable end-to-end" is satisfied by `target/` running standalone via
  `uvicorn` + `pip install -r requirements.txt`, independent of the
  orchestrator that produced it — verified with a live HTTP session (curl)
  in the root [README.md](../README.md).
- `AutoApproveProvider` is the CLI's default so the working prototype runs
  unattended for grading; `--interactive` / `asdlc resume --reject` prove
  the approval gate has real teeth when a human is actually in the loop
  (see `tests/orchestrator/test_governance.py::
  test_deny_all_provider_halts_release_stage` and `tests/test_cli.py::
  test_resume_reject_fails_the_stage_and_promotes_nothing`).

## Limitations

See [TESTING.md § Limitations](TESTING.md#limitations) for the complete,
current list: negation-blind requirement parsing, lexical-only brownfield
reasoning, entry-point approval checkpoints modeled but not yet enforced at
dispatch, minor cross-run finding-count non-determinism from genuine
parallel execution, single-process (non-distributed) execution, and the
Anthropic provider being unverified against a live API in this submission.

None of these were discovered and hidden — each is paired with the test or
transcript that surfaced it, and the fix (where one was in scope) shipped in
the same commit as the finding.
